# deploy

`docker-compose.yml` and infrastructure init scripts for the single-VM deployment (SAD 12.2)
and its environments (SAD 12.3). No secrets live here; values come from `.env` (copy
`.env.example`).

## Start and stop

Run every command from the repository root. Compose looks for `.env` next to the compose file,
not in the working directory, so always pass the root file with `--env-file`:

```bash
docker compose --env-file .env -f deploy/docker-compose.yml up -d          # postgres, rabbitmq, kong
docker compose --env-file .env -f deploy/docker-compose.yml --profile services up -d --build
docker compose --env-file .env -f deploy/docker-compose.yml ps
docker compose --env-file .env -f deploy/docker-compose.yml down           # keeps pg-data, mq-data
docker compose --env-file .env -f deploy/docker-compose.yml down -v        # also deletes the data
```

Without a profile only the infrastructure starts. The seven application services
(`identity-svc` ... `analytics-svc`, SAD 12.2) are pre-declared behind the `services` profile;
each builds from `services/<name>/Dockerfile` with the repository root as context (uv
workspace, ADR-12, ADR-14), listens on container port 8000 and has a healthcheck on
`/health/ready` (SAD 13.2). Skeleton tasks add the Dockerfile only and do not edit this file.

## Ports

Only Kong's proxy is published, on host port `${KONG_PROXY_PORT}` (SAD 8.2, 13.1). The Kong
admin API listens on the container loopback only. PostgreSQL, RabbitMQ (AMQP and management UI)
and the services are reachable only on the `internal` network.

## Components

| Service | Image | Notes |
| --- | --- | --- |
| `postgres` | `pgvector/pgvector:0.8.1-pg16` | Volume `pg-data`; init scripts from `postgres/init/` |
| `rabbitmq` | `rabbitmq:3.13.7-management` | Volume `mq-data`; fixed hostname so the node keeps its data (ADR-05) |
| `kong` | `kong:3.9.1` | Open source, DB-less, `gateway/kong.yml` mounted read-only (ADR-06) |

RabbitMQ starts empty apart from its user: the exchange `domain.events`, the queues, retry
queues and DLQs of SAD 7.3 are declared by the services through `libs/platform`.

## PostgreSQL init script

`postgres/init/01-create-service-databases.sh` runs once, on the first start with an empty
`pg-data` volume. It creates one database and one login role per service (SAD 8.1, ADR-03):
`identity_db`/`identity`, `restaurant_db`/`restaurant`, `catalog_db`/`catalog`,
`conversation_db`/`conversation`, `order_db`/`order`, `notification_db`/`notification`,
`analytics_db`/`analytics`. Each role owns its database, is not a superuser and cannot create
databases or roles. `CONNECT` is revoked from `PUBLIC` on every database (including `postgres`
and `template1`), so a role can connect only to its own database. The superuser also creates
the `vector` and `pg_trgm` extensions in `conversation_db` (SAD 8.1, 9.1).

Passwords come from `<SERVICE>_DB_PASSWORD` and must match the `<SERVICE>_DB_URL` values. The
script is idempotent; re-run it against a running server with:

```bash
docker compose --env-file .env -f deploy/docker-compose.yml exec postgres \
  bash /docker-entrypoint-initdb.d/01-create-service-databases.sh
```

Re-running creates only what is missing and never changes an existing role's password. To
apply new passwords, change them with `ALTER ROLE` or recreate the volume (`down -v`).
